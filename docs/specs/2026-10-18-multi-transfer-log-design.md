# 多演员传输与操作日志（Issue #42）

## 用户目标与交互

演员 A 传输时仍能选择 B 并提交。按用户确认，默认同时运行三个演员任务，后续任务按提交顺序等待，每个任务内部仍依次传输影片。某任务冲突或用户停止，只影响该任务；已接受的任务绑定当时的 batch、演员、目标和目录身份，之后切换页面或 batch 不改变它。

新增独立「任务与日志」页面，包含任务／日志页签。每个演员任务显示来源与目标、当前影片、阶段、已完成数量、字节进度、等待／运行／完成／停止／失败／待核对状态，支持查看目录、展开逐影片结果、独立停止。底部仅显示活动任务数量和入口，不压缩双栏目录。清理结果弹窗继续只列实际删除名称，详细结果在日志中查看。

日志记录本应用发起的归档和空目录清理操作：任务接受／开始／停止／冲突／结束，影片目标提交，源文件和目录删除，空演员目录删除及保留／跳过／失败。普通页面点击、查询轮询和字节进度不作为操作日志。日志保存在本机库，不自动清除，支持分页及任务／操作／结果筛选。未来扩展扫描、双开或设置变更不影响事件结构。

## 并发与目录所有权

- 每个任务独立 stop event、工作副本、异常快照和线程；三个执行名额，等待任务不创建阻塞工作线程。
- admission 锁串行化接受、调度、停止、清理保留与退出；SQLite 共用短期 db_lock，不在 DB 事务内执行 NAS I/O。
- 所有等待／运行任务都占有源和目标演员目录。比较规范化路径与目录身份，拒绝源源、目标目标、源目标相同或祖孙重叠；不同影片也不绕开演员目录所有权。同名演员不等于同一任务。
- 启动前再次检查既有目录身份，保留 SHA-256、无覆盖提交、ADS／reparse 防护、精确源清理；已接受任务不因切换 batch 被改写。
- 线程启动失败必须释放名额并留下可查询的失败状态。工作线程实际退出／收尾后才释放占用。
- 任一任务持久化失败时，冻结新入队与调度，通知所有正在运行的任务在安全边界停止；返回逐任务内存故障快照，保留最后持久状态供下次核对。
- 清理仍独占写入，任何等待／运行／恢复／收尾传输都会阻止清理；清理进行时禁止接受传输。

## 恢复、幂等与退出

提交 request_id 始终幂等，客户端按 request_id 独立记录未确认请求及原始 body。提供精确请求查询，不能靠 latest 判断是否已接受。只读查询可以重试，写操作仅由明确点击触发；重试确认使用原始 request_id／context／names。

重启核对全部中断记录，不自动续传、续删或启动旧等待队列。恢复独占调度，逐项核对结果；故障时仍让所有阻塞任务获得可查询的待核对报告。

保留 Rust 已有严格退出协议 `{safe, task_id, operation}`。task_id 是代表性阻塞任务，不代表唯一任务。safe 只在 admission 内确认所有任务、真实线程、恢复和清理均停止后设置；日志同步落盘，没有独立后台日志线程。前端等待所有任务，并最终调用 close_if_idle。停止全部只停止当次明确请求覆盖的活动集合，后来接受的任务必须继续显示并等待用户决定，不能误停或忽略。

## 持久日志与真实性

数据库 v3 → v4 事务迁移新增 append-only 操作事件表，保留原索引、设置和 archive_tasks。每条事件包含唯一事件键、时间、任务 ID、类别、操作、结果、演员／影片名称、源与目标路径和简洁说明。按递增事件 ID 分页，新增事件不导致翻页重复；事件键让重复幂等请求不重复记日志。

目标提交和每次删除使用成对的「准备执行／已确认成功」事件：准备事件必须先持久化，再执行原有经过验证的文件系统操作，系统调用成功返回后才能记成功。失败或中断的准备记录不能被展示为已删除。成功回执落盘失败立即停止后续动作，最后持久意图与原传输 journal 保留；启动后将未闭合操作标为待核对，不执行删除补偿。

复制完成、目标已校验提交和源已清理分别记录，不推断为等价状态。源清理部分失败时，能回查已确认的单文件／子目录删除，未完成部分保持待检查。清理日志挂在原生删除边界，非空／跳过条目如实记录；不扩展删除权限。

## API 合同（设计草案）

- `GET /api/archive/transfers?before_id=&limit=50`：`{active,history,next_cursor,busy,blocked_reason,concurrency}`。active 为完整活动集合（含终态但线程仍收尾），history 为按 archive_tasks.rowid 倒序、严格小于 before_id 的历史且排除 active。busy 覆盖真实工作器／恢复，blocked_reason 表示恢复、关闭或持久故障的准入阻止。客户端不能只根据状态推导安全空闲。
- `GET /api/archive/transfers/by-request/{request_id}`：返回对应任务或 null，位于动态任务 ID 路由前。
- 保留 latest、按 ID 查询、单任务 stop；`POST /transfers/stop-all` 接受明确 `{task_ids}` 并回显同一组合法 ID（含已终态），先完整验证再停止。丢响应后只重试原集合，不能重新捕获后来入队的任务。
- `GET /api/archive/logs`：`{items,next_cursor}`，按严格 id < before_id 游标、task_id、action、outcome 筛选，只读且受会话鉴权。事件含 id、event_key、operation_id、created_at、task_id、kind(transfer/cleanup)、action、outcome(started/succeeded/failed/skipped/stopped/needs_review)、performer_name、item_name、source_path、target_path、message。operation_id 关联准备及结果事件；started 显示准备、结果未确认。查询失败显示错误；切换筛选重置游标，旧页不混入新事件。
- 所有扩展字段经 OpenAPI 与客户端同步；退出响应不加字段，避免旧 Rust 的 deny_unknown_fields 拒绝。

## 验证与交付

设计质询后先构造关键 RED：三个真实独立任务同时推进、第四个排队、独立停止／冲突、同源／同目标／交叉重叠拒绝、请求响应丢失精确恢复、线程启动失败、日志写前与写后失败、全部任务退出与清理互斥、恢复不续写。

测试只使用临时目录／隔离数据库；任何 pytest 外服务启动必须设置临时 FILMPAW_DB。旧库迁移原数据保留、日志不虚报、分页无重漏；界面覆盖多演员切换、逐项进度、不同任务停止、日志筛选和最大化目录尺寸。按项目流程运行相关回归、Windows CI、CTO 与 Kimi K3 唯一外审。默认 PR 留待审阅，不安装应用。

## 设计质询

第一轮：后端和 UI 均为单任务全局状态，不能只去掉按钮禁用；退出 Rust 严格反序列化不能直接扩字段；必须分离 request_id 未确认状态；清理内存任务不能承担历史日志。以上已纳入设计。

第二轮：固定 stop-all 的明确 ID 集合，避免丢响应重试扩大停止范围；补齐分页、忙态和事件配对合同。by-request 返回 null 不撤销原请求，因为 POST 可能仍在途；多个未知请求分别保存，其他任务成功不能覆盖。持久故障同时冻结无 worker 的等待任务，保证停机后可退出；清理日志异常走独立 fatal 路径，不能当单目录失败继续删除。共享 NAS 父目录句柄兼容性使用真实并发临时夹具验证。活动任务总量（等待＋运行）最多 100。

用户最终确认：同时 3 个演员、其余排队；日志长期保存在本机，记录归档、源删除、空目录清理、失败、停止和冲突，冲突只停止对应演员任务。初版两个执行槽的默认假设已被此确认替换。
